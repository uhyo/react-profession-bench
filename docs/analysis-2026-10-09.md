# 分析 2026-10-09: 010 の天井、コンポーネント設計の差、そして weighted_score の挙動

第19回 §12 の項目3・4に答えるための分析。**新しい実行は一切していない**——`results/` に残っている 1561 件のアーカイブ（うち判定結果つき 1030 件）と `scores/` のスコアファイルだけを読んだ。`results/<run>/evaluation-result.json` には判定理由（`categories[].justification`）、`anti_patterns_observed`、`strengths` がすべて保存されている。

結論は3つあり、3つめは探していなかったものである。

## 1. スペック 010 の天井（90点）は本物だが、到達可能である

009 の「天井」は Claude 系の天井にすぎず、Sol max が 93 で破った（第19回 §5）。010 も同じかを確認した。

**010 のアーカイブ79件で、5点が一度も出ていないカテゴリが2つある。**

| カテゴリ | 010 での歴代最高 | 分布 |
|---|---|---|
| パフォーマンス意識 | **4/5** | 3点が71件、4点が8件、**5点は0件** |
| コンポーネント設計 | **4/5** | 5点は0件 |
| 他の4カテゴリ | 5/5 | 到達済み |

他の条件と比べた相対値でも、010 はパフォーマンス意識が**全条件で一貫して1点前後低い**（自条件の平均との差: Opus 5.5 max −1.00、Sonnet 5.5 max −1.31、Opus 5 max −1.31、Sol max −1.00、Astra max −0.92、Fable 5.1 −0.81）。ベンダ非依存の一様な低下である。

ただし 008 とは性質が違う。008 は**構造的に不可能**（`noUnusedParameters` と「data-model.ts を変更するな」が両立しない、§7 of 第19回）。010 で減点されているのは、**やれば取れるが誰もやっていないこと**である。歴代最高 010（Opus 5.5 high の 90点）の判定理由がそれを端的に示している:

> `useMemo` is applied to all genuinely expensive computations... Two minor gaps: `TreeItem` has no `React.memo`, so changing `selectedId` causes the entire flat list to re-render, and there is no `useDeferredValue` on the search input.

つまり 010 の 90 は「ツリーの行コンポーネントを `React.memo` で包んでいない」ことによる上限である。判定者は `virtualization` / `windowing` を一度も要求していない（79件の理由文に出現0回）。要求されているのは `React.memo` + `useCallback` + 派生値の `useMemo` という、ごく標準的な手当てだけである。

010 のスペック別重みは `state 15 / effect 5 / component 20 / typescript 15 / performance 15 / accessibility 30`（§3 参照）。これで天井を分解すると、観測値とぴたり一致する。

| 構成 | 得点 |
|---|---:|
| 歴代最高の実際の内訳（perf 3、comp 4、他5） | **90** ← 実測の歴代最高と一致 |
| 各カテゴリの歴代最高を全部集めた架空の実装（perf 4、comp 4） | 93 |
| perf と comp も 5 にした場合 | **100** |

- パフォーマンス意識 3 → 5 で **+6点**（重み15%）
- コンポーネント設計 4 → 5 で **+4点**（重み20%）

**結論: 010 の天井はスペックや評価基準の欠陥ではない。本当に誰も行コンポーネントをメモ化していないだけで、そこに10点が落ちている。** 009 のように「別ベンダが破る」余地はあるが、破るのは新世代である必要すらなく、既存モデルが `React.memo` を1箇所書けば 90 を超える。

## 2. コンポーネント設計の差は特定スペックのせいではなく、逆向きの失敗である

第19回 §4 で、OpenAI 系最高条件（Sol max 3.95）と Claude 系（Opus 5.5 max 4.85 / Sonnet 5.5 max 4.72）の差が唯一埋まっていない項目だと書いた。これが一つの癖なのか、散在しているのかを調べた。

**散在している。スペック単位では 12/13 で Sol max が Opus 5.5 max を下回る**（唯一の引き分けは 009、両者 4.00）。

| | |
|---|---|
| Sol max が下回ったスペック | **12/13** |
| 差の範囲 | −0.33（012, 013, 010）〜 **−2.00（008）** |
| 平均差 | −0.90 |
| Opus 5.5 max が 5.00 満点を取ったスペック | **11/13** |
| Sol max が 5.00 を取ったスペック | **0/13**（最高 4.67） |

特定スペックの事故ではなく、**全スペックに及ぶ一般的な癖**である。

### 何を減点されているのか

OpenAI 系4条件（110件）と Claude 系3条件（106件）のコンポーネント設計の理由文を、出現パターンで分類した。

| 指摘 | OpenAI | Claude |
|---|---:|---:|
| **インライン関数で描画、コンポーネントに切り出していない** | **40%** | 5% |
| **ファイルが大きすぎる / App.tsx に全部入っている** | **28%** | 3% |
| prop のバケツリレー | 14% | **44%** |
| `React.memo` がない | 5% | 0% |
| マークアップ・ロジックの重複 | 6% | 10% |

**二つのベンダは逆方向に失敗している。** OpenAI 系は**分解が足りない**（1ファイルにインライン関数で書く）。Claude 系は**分解しすぎて prop を引き回す**（44%）。

そして分解不足のほうが高くつく。理由は 010 の分析と同じで、インライン関数には `React.memo` を適用できないため、**同じ癖がパフォーマンス意識でも減点される**。Sol max の 010 の理由文がまさにそれを言っている:

> because `renderItems` is an inline function rather than a separate `TreeNode` component, `React.memo` cannot be applied to subtrees — every state change re-renders the entire tree.

**結論: 「コンポーネント設計 0.9点差」は、単一の癖——描画をインライン関数で書き、コンポーネントに切り出さない——にほぼ還元できる。** これは2カテゴリに二重計上される（重みはスペック別で、コンポーネント設計が平均 18.5%、パフォーマンス意識が平均 12.7%、合わせて **31.2%**）。prop drilling で減点される Claude 系の癖は、1カテゴリにしか効かない。

そしてこの2カテゴリは、本ベンチで**実際に点が落ちている場所の筆頭**である。カテゴリごとに「重み × （5 − 平均点）」を13スペック分合計すると:

| カテゴリ | 失っている点 | 平均重み | 平均点 |
|---|---:|---:|---:|
| **コンポーネント設計** | **64.8** | 18.5% | **3.63** |
| Effect 衛生 | 54.6 | 18.5% | 4.11 |
| アクセシビリティ | 47.8 | 17.3% | 4.00 |
| **パフォーマンス意識** | **38.7** | 12.7% | 3.70 |
| 状態設計 | 19.6 | 15.8% | 4.54 |
| TypeScript 品質 | 14.5 | 15.8% | 4.68 |

合計 239.9 点が未回収で、**そのうち 103.5 点（43%）がこの一つの癖が効く2カテゴリに集まっている。** コンポーネント設計は平均点が最も低く（3.63）、落ちている点も最大である。

## 3. 探していなかった発見: 005/006 が低いのは、評価基準がそう設計されているから

**先に訂正を1件。** この分析の初稿で私は「`weighted_score` が 005/006 でカテゴリ点から説明できない」「`expected-signals.json` は存在しない」と書いた。**どちらも誤りだった。** ファイルは `specs/<spec>/` ではなく **`evaluation/<spec>/expected-signals.json`** にあり（`runner/run.ts:283` が読んでいる）、13スペックすべてに `rubric_weights` が定義されている。私は間違ったディレクトリを探し、存在しないと結論していた。

正しい重みを当てると、**判定者の計算は完全に再現できる。**

| 予測モデル | 1030件での平均絶対誤差 |
|---|---:|
| **スペック別の実際の重み** | **0.05**（11スペックで 0.00、005 で 0.14、006 で 0.47） |
| 6カテゴリの単純平均（初稿のベースライン） | 3.13 |
| 評価基準の見出しが書いている重み（25/20/20/15/10/10） | 3.64 |

つまり `weighted_score` は決定論的であり、判定者の算術は正しい。初稿の「機構は未解明」も「仮説4つを棄却」も、**間違ったベースラインを基準にしていたせいで生じた見かけの謎**だった。

### では 005/006 で何が起きているのか

重みはスペックごとに意図的に変えられている。005 と 006 は**両方とも Effect 衛生に 30% を置いており、これは全スペック・全カテゴリ中で最大の重み付けである。** そして Effect 衛生は、まさにその2スペックで実装が最も弱いカテゴリである。

| スペック | Effect衛生の重み | Effect衛生の平均点 | 判定者の平均点 |
|---|---:|---:|---:|
| 005-system-status-dashboard | **30%** | **3.51**（13スペック中2番目に低い） | 70.5 |
| 006-notification-activity-feed | **30%** | **3.37**（最低） | 69.4 |
| 参考: 010 | 5% | 4.44 | 76.7 |
| 参考: 012 | 15% | 4.89 | 92.1 |

**005/006 のスコアが低いのは、スコアリングの事故ではなく評価基準の設計通りである。** この2スペックは Effect 衛生を主に測るために作られており、モデルは Effect 衛生が苦手で、重みがそれを増幅する。

### 前言の撤回

初稿にもとづいて私は「005 と 006 を『未解決スペック』と呼んでいたのは相当部分がスコアリングの産物」と述べた。**これは撤回する。** 逆である——この2スペックが低いのは、設計上もっとも重い項目でモデルが実際に失敗しているからで、第17回の「未解決スペック」の並びは正しかった。

カテゴリ単純平均で並べ替えると 005 が中位に見えるのは事実だが、それは**各スペックが何を測ろうとしているかを無視した並べ替え**にすぎない。単純平均は 005 にとって妥当な集計ではない。

### 残る本物の論点

判定者の算術が正しいことが分かったので、問うべきことは別にある。**Effect 衛生は5スペックで 25〜30% の重みを与えられている**（004, 005, 006, 007, 008）。平均重み 18.5%、平均点 4.11 で、落ちている点は 54.6 ——コンポーネント設計（64.8）に次ぐ2番目である（§2 の表）。

重要なのは性質の違いである。コンポーネント設計は**ベンダで分かれる**（OpenAI 3.95 対 Claude 4.85）。Effect 衛生とアクセシビリティは**全ベンダ共通**に落ちている。つまり「どのモデルを選ぶか」で動くのはコンポーネント設計で、「React の書き手として業界全体がまだできていないこと」はEffect 衛生とアクセシビリティ、ということになる。

## 4. Effect 衛生は、実際には「React 19 API を採用したか」を測っている

§3 で Effect 衛生が未回収54.6点の2番目だと分かったので、理由文1030件を読んだ。**カテゴリ名が指すものとは別のことを測っていた。**

13スペックはきれいに二群に分かれる。

| スペック | 平均 | 最高 | 5点の回数 | API言及率 | そのスペックが要求する API |
|---|---:|---:|---:|---:|---|
| 004-user-profile-browser | 2.86 | 5 | 7/78 | 100% | `use()` + `<Suspense>` + error boundary |
| 007-sns-feed | 3.09 | 5 | 2/77 | 100% | `useOptimistic` |
| 006-notification-activity-feed | 3.37 | 5 | 16/78 | 100% | `useEffectEvent` |
| 005-system-status-dashboard | 3.51 | 5 | 29/78 | 100% | `useSyncExternalStore` |
| 011-tooltip-popover | 3.84 | **4** | **0/81** | 100% | **HTML Popover API** |
| 008-form-actions | 3.86 | 5 | 25/77 | 96% | `useActionState` / `useFormStatus` |
| ——— 以下、要求APIなし ——— | | | | | |
| 009 / 010 / 003 / 002 / 012 / 001 / 013 | 4.16〜4.93 | 5 | 15〜79 | 平均21% | — |

**減点の低い6スペックすべてで、理由文の 96〜100% が React 19 系 API に言及している。** 要求APIのない7スペックでは 21%、平均点は 4.16〜4.93 で実質的に満点域である。

決定的なのは、判定者が**衛生そのものは合格と明言した上で減点している**ことである。

> 006 / Opus 5 max: 「All three effects (WebSocket subscription, auto-save timer, toast dismiss timer) have correct cleanup and no misuse for derived state or event handling — **that is clean.** However, both primary patterns identified for spec 006 use the ref-based workaround (`useLatestRef`) instead of `useEffectEvent`」

> 004 / Sonnet 5.5 max: 「The two effects present are **individually well-written** ... However, spec 004 specifically measures Suspense adoption」

> 011 / Opus 5 max: 「**All effects that are present do have correct cleanup** (clearTimeout, removeEventListener, disconnect), so the hygiene within the portal approach is sound, **but the approach itself necessitates effects that are unnecessary with platform APIs.**」

つまり「useEffect の使い方が下手」で減点されているのではない。**「その機能をいま書くなら使うべき API を使っていない」で減点されている。** クリーンアップ漏れ・派生stateのEffect化・依存配列の誤りといった古典的な衛生問題は、理由文の中では少数派である（5点未満の305件のうち、クリーンアップ漏れ 6%、派生state 10%）。

### 011 にはもう一つの到達不能な天井がある

011 は **81件すべてで最高4点、5点が一度もない。** 要求されているのが HTML Popover API（`popover` 属性 + `showPopover()`）で、**どのモデルも一度も使っていない**ためである。010 のメモ化（§1）と同型だが、010 は「やれば取れる」のに対し、011 は要求が React ではなくプラットフォーム API の知識である点が違う。

### 時系列で見ると「学習して追いつく」挙動ではない

API要求6スペックと、要求なし7スペックで、条件別に Effect 衛生の平均を分けた（ベンチ実施日順）。

| 時期の代表条件 | API要求スペック | 要求なしスペック | 差 |
|---|---:|---:|---:|
| opus-4.8-max（5月） | 3.72 | 4.86 | −1.13 |
| gpt-5.6-terra-max（7月） | 2.94 | 4.81 | −1.87 |
| opus-5-max（7月） | 4.17 | 4.86 | −0.69 |
| **opus-5.5-max（9月）** | **4.44** | 4.90 | **−0.46** |
| gpt-6.1-sol-max（10月） | 3.67 | 4.95 | −1.29 |
| gpt-6-luna-max（10月） | 3.00 | 4.71 | −1.71 |

**カレンダー上の単調な改善はない。** 10月の GPT-6 Luna（3.00）は7月の GPT-5.6 Luna（3.00）と同じで、最良は9月の Opus 5.5 max（4.44）である。つまりこれは「新しいモデルほど新しい API を知っている」という時間効果ではなく、**モデルの能力そのものを測る軸**として働いている。

同時に重要なのは、**要求なし7スペックが全条件 4.48〜4.95 で飽和している**ことである。古典的な Effect 衛生は、2026年のモデルにとって解決済みの問題で、識別力がない。識別しているのは API 採用の側だけである（幅 2.83〜4.44）。

## 6. v2 設計への含意

この分析は v2 の設計材料として行った。優先度順に。

### 6.1 Effect 衛生を2つに割る（最重要）

現状の `effect_hygiene` は、識別力のまったく違う2つのものを1カテゴリに混ぜている。

| | 対象スペック | 全24条件での範囲 | 識別力 |
|---|---|---|---|
| 古典的な衛生（クリーンアップ、依存配列、派生state） | 要求APIなしの7スペック | **4.48 〜 4.95** | **ほぼゼロ（飽和）** |
| React 19 API の採用 | 要求APIのある6スペック | **2.83 〜 4.44** | **大（幅1.6）** |

**しかもこの API 採用軸が、順位表の上端を決めている。** Opus 5.5 max と Sonnet 5.5 max の差（94.46 対 91.74）に最も効いている2セルは、006 の Effect 衛生（+1.33、重み30%）と 004 の Effect 衛生（+0.67、重み25%）である——どちらも API 要求スペックである。

提案: カテゴリを `effect_hygiene`（飽和しているので低い重みの衛生フロアとして残す）と **`modern_api_adoption`（新設、本来の識別軸）** に分ける。名前が測っているものと一致していないことが、今回私自身を混乱させた最大の原因である。

### 6.2 API 要求に「いつから存在する API か」を併記する

要求される API は `useEffectEvent`（React 19.2）から HTML Popover API（プラットフォーム側）まで幅がある。現状の `expected-signals.json` は API 名を書いているが**バージョンを書いていない**。

時系列で見ると「新しいモデルほど採用する」という単調な傾向はなく（§4）、能力軸として機能している。しかし React が API を追加し続ける限り、**同じ `effect_hygiene` という名前のスコアが、年をまたぐと別のものを測っている**状態になる。第19回 §8 の CLI バージョンと同じ種類の問題で、測定器の一部が記録されていない。v2 では expected-signals に `introduced_in: "19.2"` 相当を持たせ、スコアをモデルの知識カットオフと突き合わせて読めるようにすべきである。

### 6.3 到達不能な天井を意図的に決める

| スペック | 天井 | 性質 | 判断 |
|---|---|---|---|
| 010 パフォーマンス意識 | 5点が0/79 | **到達可能。** 行コンポーネントを `React.memo` で包むだけ（§1） | 残す。「標準的な手当てを誰もしない」自体が測定結果 |
| 011 Effect 衛生 | **5点が0/81、最高4点** | HTML Popover API を**どのモデルも一度も使わない**（§4） | 要判断。恒久的に取れない4点上限を全条件に課している |
| 008 コンパイル | 非コンパイル33/36件 | **構造的に不可能**（第19回 §7） | 修正する |

011 は「業界が知らない API を測る」ことに価値を認めるなら残す、順位の分解能を優先するなら要求を緩める。**どちらでもよいが、意図せずそうなっている現状は避けるべきである。**

### 6.4 アクセシビリティを他カテゴリの手本にする

§5 の通り、アクセシビリティは唯一「連続的・到達可能・ベンダ中立・天井なし」である。13スペックすべてで5点の実例があり、点の分布が連続で、減点は網羅性の不足として説明できる。**v2 の他カテゴリもこの性質を目指すべきである**——二群に割れていたり（Effect 衛生）、永久に取れない上限があったり（011）しない形。

### 6.5 コンポーネント設計は最大の未回収点であり、最大のベンダ差でもある

64.8点（全未回収239.9点中）。平均点3.63で最低。しかも **OpenAI 3.95 対 Claude 4.85 と、唯一ベンダで割れる軸**である（§2）。機構も特定済み——描画をインライン関数で書き、コンポーネントに切り出さない癖で、これが `React.memo` を阻害してパフォーマンス意識にも二重に効く。

v2 ではこの癖を直接測る期待シグナルを置ける（「描画が別コンポーネントに切り出されているか」「メモ化可能な境界があるか」）。現状は副作用として観測されているだけである。

### 6.6 `rubric.md` の見出しの重みを直す
