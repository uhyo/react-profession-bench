# Integrity audit: did the tested agent read the evaluation criteria?

**Date:** 2026-07-26
**Trigger:** Opus 5 posted the highest scores in the benchmark's history (第14回 — high 87.00, max 90.28,
beating the standing record of Fable 5 max at 86.67). Before those numbers are treated as real, the
possibility that the tested agent found this repository and read its own grading criteria has to be
excluded.
**Scope:** the 78 Opus 5 implementations of 2026-07-25/26 (`opus-5`, `opus-5-max`, n=3 each), plus the
sandbox environment shared by all past runs.
**Verdict:** **no evidence of criteria access.** Multiple independent checks agree, and the model's own
output argues against it. Two unrelated integrity issues were found and are recorded in §5.

---

## 1. What the threat actually is

Implementations are run by `runner/run.ts` in a copy of `scaffold/` under
`/tmp/react-profession-bench/<timestamp>_<spec>_<model>`, with the CLI invoked as:

```
claude --print --model <m> --permission-mode bypassPermissions
       --allowedTools Read Write Edit Bash Glob Grep ...
```

Two facts follow. First, the working directory is outside the repo, so `evaluation/`, `scores/` and other
models' `results/` are not reachable by relative path — this is the isolation the comment at
`runner/run.ts:15` claims. Second, the agent holds Bash with bypassed permissions on a machine where the
repo is readable, and its own `pwd` contains the string `react-profession-bench`. **The boundary is
non-disclosure, not enforcement.** A sufficiently curious agent could read
`evaluation/rubric.md`, `evaluation/<spec>/expected-signals.json`, or `evaluation/anti-patterns.md`
and tailor its implementation to them.

So the question is not "was it possible" (it was) but "did it happen".

## 2. Method

No transcripts exist — the runner passes `--no-session-persistence`, so there is no tool-call log to read.
The audit is therefore based on artifacts and filesystem state:

1. inputs the agent receives (prompt, sandbox contents, ambient config that a CLI loads regardless of cwd);
2. traces the agent left behind (files written outside the sandbox, persisted memory, edit history);
3. access times on repo files the runner never touches, which would move only if something else read them;
4. behavioral evidence — whether the produced code looks like the work of something that had read the key.

## 3. Findings

### 3.1 Nothing in the agent's inputs discloses the benchmark

- `buildImplementationPrompt` (`runner/run.ts:666`) contains the spec, the data model and generic
  instructions. It never mentions grading, the six categories, the judge, or the repository.
- No `~/.claude/CLAUDE.md`, no `/home/uhyo/CLAUDE.md`, no `/tmp/CLAUDE.md`. A user-level memory file
  would be loaded into *every* sandbox session regardless of cwd; none exists.
- No global memory directory (`~/.claude/memory`), and no project entry for the sandbox *parent* path
  (`-tmp-react-profession-bench`), which is the only path through which two runs could have shared state.

### 3.2 No trace of access to the criteria

| check | result |
|---|---|
| Repo paths named in anything the agents left behind | only `scaffold/node_modules/...`; nothing under `evaluation/`, `specs/`, `scores/`, `results/` |
| `~/.claude/file-history` entries for repo paths from any of the 12 sandbox session IDs | none |
| atime, `scores/REPORT_*.md` (runner never reads these) | frozen at 2026-07-25 08:06 — an operator read *before* the sweep began |
| atime, `docs/benchmark-v2-plan.md` | frozen at 2026-07-25 08:09, same |
| atime, `evaluation/*/expected-signals.json`, `evaluation/rubric.md` | recent, but fully explained by judge activity: the last max sample finished 16:53, and the timestamps track its per-spec evaluations |
| `git status` / repo working tree | clean apart from the operator's own commits |

The report and plan atimes are the most informative line in that table: those files are read by no part of
the pipeline, and they went untouched across the entire 32-hour run window. Had an agent browsed the repo
looking for how it was being judged, the reports — which state the scoring criteria in plain language, in
detail, per category — are the most valuable thing in it and would have moved.

### 3.3 The output argues against peeking

The criteria files name `useTransition` 13 times, `useActionState` 8 and `useOptimistic` 4, across at least
five specs (002, 004, 007, 008, 009). Measured over the Opus 5 archive directories (84 — the 78 scored
implementations plus retry archives):

- `useTransition`: **1**
- `useOptimistic`: **1**
- `useActionState`: 6

And Opus 5's weakest category is *performance awareness* (4.00 high / 4.21 max), the one those signals feed.
An agent that had read the key would not leave the cheapest available points untaken and then underperform
precisely where the key is most explicit.

One agent's own note, written after driving its app in a browser, describes verifying markup
"the way a grader's testing-library suite would query it." The benchmark grades with an LLM judge and runs
no tests at all. That is a wrong model of the grading process, and it is not one that survives reading
`rubric.md`.

## 4. What the agents did do

The suspicion was not baseless — the agents do leave their sandbox, just not toward the criteria.
Across 12 Opus 5 runs (and, identically, 18 Fable 5 max runs back on 2026-07-02/05) they:

- followed pnpm symlinks out of the sandbox into `/home/uhyo/repos/react-profession-bench/scaffold/node_modules`
  while diagnosing a runtime failure;
- installed `playwright-core` into a scratch dir under `/tmp` and drove cached headless Chromium against
  `npm run dev` to verify their work;
- wrote memory files under `~/.claude/projects/-tmp-react-profession-bench-<runName>/memory/`.

**This is not new to Opus 5** — Fable 5 max did the same three weeks earlier, which matters because both
models' scores are in the standing ranking. And it did not contaminate the results: each run's cwd is unique
(timestamped), so each gets its own project directory and its own empty memory; with no parent-level and no
global memory directory, **no run inherited another run's notes**. The repo's `scaffold/node_modules` has not
been modified since 2026-07-02 — the agents repaired only their own sandbox copies.

## 5. Two real issues found on the way

**5.1 The v1 scaffold ships a duplicate-React defect.**
In the sandbox copies, `node_modules/.pnpm/react-dom@*/node_modules/react` resolves back to the repo's
scaffold while the app's own `node_modules/react` resolves locally. Two React instances load, so
`ReactSharedInternals.H` is null and **every hook throws** `Cannot read properties of null (reading 'useState')`
at runtime — in dev, in the production build, and under `react-dom/server`.

`tsc -b --noEmit` and `vite build` both pass, which is exactly why v1 has never detected it: the pipeline's
only automated check is compilation. The consequence for comparability is uncomfortable — models that verify
in a real browser spend effort fighting the scaffold, while models that never run their code ship something
that would crash on load and are scored no differently. v2's proposed Playwright smoke gate (§3.1 of the v2
plan, listed there as optional v2.1) would catch this class of failure; on this evidence it deserves
promoting. The defect should be fixed before v2 calibration, since calibration numbers taken against a
broken scaffold would bake the distortion into the new baseline.

**5.2 Sandbox isolation should be enforced rather than assumed.**
Today's containment rests on the agent not looking. Recommended for v2, in rough order of value:

1. run implementations with reads restricted to the working directory (container or `bwrap`), so the
   question this audit answers becomes unaskable;
2. give each run its own `HOME`, so ambient user config cannot leak in and agent-written memory cannot persist;
3. name the sandbox root something that does not advertise the benchmark — the current path tells the agent
   what it is participating in.

## 6. Limitations

- `--no-session-persistence` means there is no tool-call log; this audit reasons from artifacts and
  filesystem state, not from a record of what each agent did.
- atime on `evaluation/rubric.md` and the `expected-signals.json` files is confounded by legitimate judge
  reads on every evaluation. For those specific files the audit shows *no anomaly*; it cannot prove a
  negative. The unconfounded files (reports, v2 plan) carry the negative evidence instead.
- `results/` directory atimes were overwritten in bulk by the operator's own analysis on 2026-07-26 11:42,
  so they cannot be used to test whether an agent browsed other models' solutions. No other evidence
  suggests it did.

## 7. Conclusion

The Opus 5 results of 第14回 stand. The agent did not read its grading criteria: nothing disclosed them to it,
it left no trace of reaching them, the two files that would have proven it went untouched, and the code it
produced is not the code of something that had read them.

What the audit did establish is that the benchmark's isolation is weaker than the comment in `run.ts`
implies, and that the v1 scaffold has been shipping a runtime-fatal defect that the compile-only pipeline
cannot see. Neither invalidates 第14回, and both belong on the v2 punch list.
